# User Stories — Микросервис доставки посылок


## Обозначения

- **US** — User Story (пользовательская история).
- **Приоритет**: Must / Should / Could (MoSCoW).
- **Оценка**: в story points (SP), шкала Фибоначчи.

---

## Акторы

| Актор | Описание |
|-------|----------|
| **Пользователь** | Анонимный клиент сервиса. Идентифицируется по сессии (cookie). Не проходит авторизацию. |
| **Служба поддержки (RAG)** | Виртуальный ассистент, отвечающий на вопросы на основе базы знаний и LLM. |
| **Планировщик (Scheduler)** | Системный компонент, запускающий периодические задачи. |
| **Внешний сервис курса валют** | `https://www.cbr-xml-daily.ru/daily_json.js` — источник курса USD/RUB. |
| **LLM-провайдер** | Внешний или локальный API генерации ответов. |
| **Транспортная компания** | Внешний актор доп. задания (привязка посылки к компании). |

## US-01. Регистрация посылки

**Как** пользователь,
**я хочу** зарегистрировать посылку, указав название, вес, тип и стоимость содержимого,
**чтобы** получить её индивидуальный идентификатор и в дальнейшем отслеживать её.

**Приоритет:** Must
**Оценка:** 5 SP

**Детали:**
- Входные данные — JSON.
- Обязательные поля: `name`, `weight`, `type`, `content_cost_usd`.
- Валидация входных данных обязательна.
- При успехе возвращается индивидуальный `id` посылки.
- `id` доступен только пользователю, подавшему запрос, в рамках его сессии.

**Связанные требования:** роут «Зарегистрировать посылку», обязательное требование «Приложение отслеживает пользователей по сессии».

---

## US-02. Получение справочника типов посылок

**Как** пользователь,
**я хочу** получить список всех типов посылок с их идентификаторами,
**чтобы** корректно указывать тип при регистрации и фильтрации.

**Приоритет:** Must
**Оценка:** 2 SP

**Детали:**
- Типы: `одежда`, `электроника`, `разное`.
- Типы хранятся в отдельной таблице БД.
- Возвращаются `id` и название типа.

**Связанные требования:** роут «Получить все типы посылок и id типов».

---

## US-03. Просмотр списка своих посылок

**Как** пользователь,
**я хочу** получить список своих посылок со всеми полями, включая имя типа и стоимость доставки,
**чтобы** видеть состояние всех своих отправлений.

**Приоритет:** Must
**Оценка:** 8 SP

**Детали:**
- Возвращаются только посылки текущей сессии.
- Поля: `id`, `name`, `weight`, `type` (имя), `content_cost_usd`, `delivery_cost` (или «Не рассчитано»).
- Обязательна **пагинация**.
- Обязательна **фильтрация**:
  - по типу посылки;
  - по факту наличия рассчитанной стоимости доставки.

**Связанные требования:** роут «Получить список своих посылок».

---

## US-04. Просмотр данных о посылке по id

**Как** пользователь,
**я хочу** получить детальные данные о конкретной своей посылке по её `id`,
**чтобы** проверить её параметры и стоимость доставки.

**Приоритет:** Must
**Оценка:** 3 SP

**Детали:**
- Возвращаются: `name`, `weight`, `type`, `content_cost_usd`, `delivery_cost`.
- Доступ только к посылкам своей сессии (иначе — ошибка доступа/не найдено).

**Связанные требования:** роут «Получить данные о посылке по ее id».

---

## US-05. Вопрос службе поддержки (RAG)

**Как** пользователь,
**я хочу** задать текстовый вопрос службе поддержки,
**чтобы** получить ответ о правилах таможни и доставки.

**Приоритет:** Must
**Оценка:** 13 SP

**Детали:**
- Эндпоинт принимает текстовый вопрос (например, «Можно ли отправить ноутбук?», «Какие ограничения на вес?»).
- Система векторизует запрос.
- Выполняется векторный поиск по заранее загруженной базе знаний (фиктивный текстовый файл с правилами таможни и доставки).
- Найденный контекст передаётся в LLM для генерации ответа.
- Ответ возвращается пользователю.

**Связанные требования:** роут «Задать вопрос службе поддержки (RAG)», обязательное требование «развернуть векторную БД», «интеграция с API LLM».

## US-06. Автоматический расчёт стоимости доставки

**Как** система,
**я хочу** раз в 5 минут выставлять всем необработанным посылкам стоимость доставки в рублях,
**чтобы** пользователи видели актуальную стоимость без ручного запуска.

**Приоритет:** Must
**Оценка:** 8 SP

**Детали:**
- Периодичность: каждые 5 минут.
- Формула: `Стоимость = (вес_кг * 0.5 + стоимость_содержимого_usd * 0.01) * курс_usd_rub`.
- Курс берётся из `https://www.cbr-xml-daily.ru/daily_json.js`.
- Курс кешируется в Redis.
- Обрабатываются только посылки без рассчитанной стоимости.

**Связанные требования:** раздел «Периодические задачи».

## US-07. Ручной запуск периодической задачи (отладка)

**Как** разработчик,
**я хочу** запускать периодическую задачу расчёта стоимости вне расписания,
**чтобы** отлаживать и тестировать логику расчёта.

**Приоритет:** Should
**Оценка:** 3 SP

**Детали:**
- Возможность запуска вне расписания.
- Предназначено для нужд отладки.

**Связанные требования:** примечание «Добавить возможность запуска периодических задач вне расписания».

---

## US-08. Отображение статуса «Не рассчитано»

**Как** пользователь,
**я хочу** видеть «Не рассчитано» вместо стоимости доставки, если она ещё не вычислена,
**чтобы** понимать состояние обработки посылки.

**Приоритет:** Must
**Оценка:** 2 SP

**Детали:**
- Если стоимость доставки не рассчитана — выводится строка «Не рассчитано».

**Связанные требования:** примечание «Если стоимость доставки еще не рассчитана — выводить "Не рассчитано"».

---

## US-09. Привязка посылки к транспортной компании (доп. задание)

**Как** транспортная компания,
**я хочу** привязать посылку к себе,
**чтобы** закрепить её за собой для доставки.

**Приоритет:** Could
**Оценка:** 8 SP

**Детали:**
- Роут добавляет `id` компании (любое положительное число) к записи посылки.
- Одну посылку могут пытаться привязать разные компании.
- Гарантия: 1-я обратившаяся компания закрепляет посылку за собой.
- Высокая нагрузка: запросы могут прилетать несколько раз в секунду (нужна защита от гонки).

**Связанные требования:** доп. задание №3.

---

## US-10. Регистрация посылок через RabbitMQ (доп. задание)

**Как** система,
**я хочу** принимать регистрацию посылок через брокер сообщений и воркеры,
**чтобы** сразу рассчитывать стоимость доставки и отказаться от периодической задачи.

**Приоритет:** Could
**Оценка:** 13 SP

**Детали:**
- Посылки из роута регистрации попадают не напрямую в БД, а через брокер.
- Воркеры обрабатывают сообщения и сразу рассчитывают стоимость доставки.
- Периодическая задача расчёта стоимости больше не нужна.

**Связанные требования:** доп. задание №2.

---

## US-11. Подсчёт суммы стоимостей доставок по типам за день (доп. задание)

**Как** аналитик,
**я хочу** получать сумму стоимостей доставок всех посылок по типам за день,
**чтобы** анализировать нагрузку и выручку.

**Приоритет:** Could
**Оценка:** 13 SP

**Детали:**
- Лог расчётов хранится в MongoDB.
- Объём: до миллиона посылок в день.
- Нужен способ подсчёта суммы по типам за день на основе лога.

**Связанные требования:** доп. задание №1.
