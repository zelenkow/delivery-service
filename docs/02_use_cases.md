# Use Cases — Микросервис доставки посылок


## Обозначения

- **UC** — Use Case (вариант использования).
- **Основной поток** — happy path.
- **Альтернативный поток** — обработка ошибок и исключений.

---

## UC-01. Регистрация посылки

**Актор:** Пользователь
**Предусловие:** Пользователь имеет активную сессию (cookie установлена автоматически).
**Постусловие:** Посылка сохранена в БД, привязана к сессии, возвращён её `id`.

### Основной поток
1. Пользователь отправляет `POST /api/parcels/` с JSON-телом.
2. Система проверяет наличие сессии; при отсутствии — создаёт новую.
3. Система валидирует поля: `name`, `weight`, `type`, `content_cost_usd`.
4. Система проверяет существование типа посылки по `type`.
5. Система создаёт запись посылки, привязывая её к сессии.
6. Система возвращает `201 Created` с `id` посылки.

### Альтернативные потоки
- **A1. Невалидные данные** → `400 Bad Request` со списком ошибок валидации.
- **A2. Несуществующий тип** → `400 Bad Request` (ошибка «неизвестный тип посылки»).
- **A3. Отрицательный/нулевой вес** → `400 Bad Request`.
- **A4. Отрицательная стоимость содержимого** → `400 Bad Request`.

**Связанные US:** US-01.

## UC-02. Получение справочника типов посылок

**Актор:** Пользователь
**Предусловие:** Нет.
**Постусловие:** Возвращён список типов.

### Основной поток
1. Пользователь отправляет `GET /api/parcel-types/`.
2. Система выбирает все записи из таблицы типов.
3. Система возвращает `200 OK` со списком `{id, name}`.

### Альтернативные потоки
- **A1. Справочник пуст** → `200 OK` с пустым массивом.

**Связанные US:** US-02.

## UC-03. Просмотр списка своих посылок

**Актор:** Пользователь
**Предусловие:** Активная сессия.
**Постусловие:** Возвращён постраничный список посылок текущей сессии.

### Основной поток
1. Пользователь отправляет `GET /api/parcels/?page=1&page_size=20`.
2. Система определяет сессию.
3. Система выбирает посылки, привязанные к сессии.
4. Система применяет фильтры (если переданы):
   - `type` — по id типа;
   - `has_delivery_cost` — `true`/`false`.
5. Система применяет пагинацию.
6. Система формирует ответ: для каждой посылки — `id`, `name`, `weight`, `type`, `content_cost_usd`, `delivery_cost` (или «Не рассчитано»).
7. Система возвращает `200 OK` с метаданными пагинации.

### Альтернативные потоки
- **A1. Некорректный номер страницы** → `400 Bad Request`.
- **A2. Некорректный фильтр типа** → `400 Bad Request`.
- **A3. Нет посылок** → `200 OK` с пустым списком.

**Связанные US:** US-03, US-08.

## UC-04. Просмотр данных о посылке по id

**Актор:** Пользователь
**Предусловие:** Активная сессия.
**Постусловие:** Возвращены детальные данные посылки.

### Основной поток
1. Пользователь отправляет `GET /api/parcels/{id}/`.
2. Система определяет сессию.
3. Система ищет посылку по `id` **в пределах сессии**.
4. Система возвращает `200 OK` с полями: `name`, `weight`, `type`, `content_cost_usd`, `delivery_cost`.

### Альтернативные потоки
- **A1. Посылка не найдена** → `404 Not Found`.
- **A2. Посылка принадлежит другой сессии** → `404 Not Found` (не раскрываем существование).

**Связанные US:** US-04, US-08.

## UC-05. Вопрос службе поддержки (RAG)

**Актор:** Пользователь
**Предусловие:** База знаний загружена и векторизована в векторной БД.
**Постусловие:** Пользователь получил сгенерированный ответ.

### Основной поток
1. Пользователь отправляет `POST /api/support/ask/` с телом `{"question": "..."}`.
2. Система валидирует непустоту вопроса.
3. Система векторизует вопрос (embedding-модель).
4. Система выполняет векторный поиск в Qdrant/ChromaDB, получает top-K релевантных фрагментов.
5. Система формирует промпт: системная инструкция + найденный контекст + вопрос.
6. Система вызывает LLM API.
7. Система возвращает `200 OK` с ответом и (опционально) источниками.

### Альтернативные потоки
- **A1. Пустой вопрос** → `400 Bad Request`.
- **A2. Векторная БД недоступна** → `503 Service Unavailable`.
- **A3. LLM недоступна/таймаут** → `502 Bad Gateway` или `504 Gateway Timeout`.
- **A4. Контекст не найден** → LLM отвечает «не знаю» на основе системной инструкции.

**Связанные US:** US-05.

## UC-06. Автоматический расчёт стоимости доставки (по расписанию)

**Актор:** Планировщик
**Предусловие:** Есть посылки без рассчитанной стоимости.
**Постусловие:** Всем необработанным посылкам проставлена стоимость доставки в рублях.

### Основной поток
1. Планировщик запускает задачу каждые 5 минут.
2. Система получает курс USD/RUB:
   - проверяет Redis-кеш;
   - при промахе — запрашивает `https://www.cbr-xml-daily.ru/daily_json.js` и кладёт в Redis с TTL.
3. Система выбирает посылки с `delivery_cost IS NULL`.
4. Для каждой посылки вычисляет: `(weight * 0.5 + content_cost_usd * 0.01) * rate`.
5. Система сохраняет `delivery_cost` и `delivery_cost_calculated_at`.
6. Система логирует результат (кол-во обработанных).

### Альтернативные потоки
- **A1. Внешний API недоступен** → используется последнее кешированное значение; если кеша нет — задача завершается с ошибкой и логируется.
- **A2. Нет необработанных посылок** → задача завершается без изменений.

**Связанные US:** US-06.

## UC-07. Ручной запуск расчёта стоимости (отладка)

**Актор:** Разработчик
**Предусловие:** Сервис запущен.
**Постусловие:** Задача расчёта выполнена вне расписания.

### Основной поток
1. Разработчик запускает management-команду (например, `python manage.py calculate_delivery_costs`).
2. Система выполняет логику UC-06.
3. Система выводит отчёт в консоль.

### Альтернативные потоки
- **A1. Ошибка внешнего API** → вывод ошибки, ненулевой код возврата.

**Связанные US:** US-07.

## UC-08. Привязка посылки к транспортной компании (доп. задание)

**Актор:** Транспортная компания
**Предусловие:** Посылка существует и ещё не привязана.
**Постусловие:** Посылка закреплена за первой обратившейся компанией.

### Основной поток
1. Компания отправляет `POST /api/parcels/{id}/assign/` с `{"company_id": 123}`.
2. Система валидирует `company_id` (положительное число).
3. Система выполняет атомарное обновление: `UPDATE ... WHERE id = ? AND company_id IS NULL`.
4. Если обновлена 1 строка — компания закрепила посылку.
5. Система возвращает `200 OK`.

### Альтернативные потоки
- **A1. Посылка уже привязана** → `409 Conflict` с id текущей компании.
- **A2. Посылка не найдена** → `404 Not Found`.
- **A3. Гонка запросов** → только один запрос успешен, остальные получают `409 Conflict`.

**Связанные US:** US-09.

## UC-09. Регистрация посылки через RabbitMQ (доп. задание)

**Актор:** Пользователь, Брокер, Воркер
**Предусловие:** RabbitMQ и воркеры запущены.
**Постусловие:** Посылка сохранена в БД со сразу рассчитанной стоимостью.

### Основной поток
1. Пользователь отправляет `POST /api/parcels/`.
2. Система валидирует данные.
3. Система публикует сообщение в очередь RabbitMQ.
4. Система возвращает `202 Accepted` с временным идентификатором.
5. Воркер получает сообщение, сохраняет посылку в БД.
6. Воркер сразу рассчитывает стоимость доставки.
7. Воркер подтверждает обработку (`ack`).

### Альтернативные потоки
- **A1. Брокер недоступен** → `503 Service Unavailable`.
- **A2. Ошибка обработки в воркере** → сообщение уходит в DLQ, логируется.

**Связанные US:** US-10.

## UC-10. Подсчёт суммы стоимостей доставок по типам за день (доп. задание)

**Актор:** Аналитик
**Предусловие:** Лог расчётов пишется в MongoDB.
**Постусловие:** Получена сумма по каждому типу за указанный день.

### Основной поток
1. Аналитик запрашивает отчёт за дату.
2. Система выполняет агрегацию в MongoDB (pipeline: `$match` по дате → `$group` по типу → `$sum`).
3. Система возвращает результат по типам.

### Альтернативные потоки
- **A1. Нет данных за день** → пустой результат.

**Связанные US:** US-11.
